# FIKISHA-V2 — Proof of Delivery: OTP, Evidence and Authorization

**Status:** Candidate implementation with synthetic Node test coverage. **Not live-integrated or production-ready.**  
**Candidate branch:** `build/proof-of-delivery-otp-evidence`  
**Base:** delivery lifecycle / offers / outbox candidate.

## Permitted state path

1. The assigned driver must be the authenticated, active driver bound to the delivery and company.
2. The delivery must already be `IN_TRANSIT`. The assigned driver records `ATTEMPT_DELIVERY`, which moves it to `DELIVERY_VERIFICATION_PENDING`.
3. Only then can the assigned driver request an OTP challenge. The server reads the recipient phone from the persisted delivery; a caller cannot choose a different phone.
4. The OTP is delivered to that recipient contact by the injected OTP sender. The API returns the challenge ID and expiry, never the OTP.
5. The assigned driver registers Drive evidence against that challenge after upload. Server-side Drive metadata and ACL checks must pass.
6. Completion requires the current OTP, an unexpired/unconsumed challenge, attempts remaining, unchanged recipient binding, at least one accepted delivery photo, and every evidence record bound to the same company, delivery, challenge and uploader.
7. Only then is a verified proof record created and the existing `VERIFY_OTP` transition requested. The Sheets store independently rechecks that proof, challenge and evidence bindings before permitting `DELIVERED_VERIFIED`.
8. The challenge becomes `CONSUMED` after transition success. A retry after an interruption must use the same idempotency key and exact evidence list. A different request cannot reuse the challenge.

No other state transition may mark a delivery as `DELIVERED_VERIFIED`. A rejected, expired, incomplete or unverified proof must leave it uncompleted.

## OTP security policy

- Six decimal digits, generated by an injected cryptographically secure random generator.
- Five-minute default expiry; five failed attempts maximum. The challenge is invalidated when expired, exhausted, superseded or OTP delivery fails.
- Store only an HMAC/MAC of the OTP, with a server-held secret key and domain-separated input including company, delivery and recipient fingerprint. Do **not** use a plain hash for a six-digit code. The recipient fingerprint is also keyed and normalized; the phone number is not copied into the challenge row.
- The OTP plaintext is passed only to the sender adapter in memory. It is never persisted or included in logs, events, errors or responses.
- The production `digestOtp` adapter must use a strong keyed HMAC with a secret held in Script Properties or another server-only secret store. `randomCode` must use a cryptographically secure source. The code intentionally requires these dependencies; it does not silently fall back to weak generation or an unkeyed hash.
- OTP attempts are serialized by the store's script lock in the Google adapter. The Node test lock is a simulation and does not prove real Apps Script contention behavior.
- Reissue invalidates an outstanding active challenge. If a challenge is in `COMPLETING`, reissue fails with a recovery-required error rather than discarding an interrupted completion.

## Evidence policy

Allowed evidence types:
- **Required:** at least one `DELIVERY_PHOTO`.
- **Optional:** `RECIPIENT_SIGNATURE`.
- **File types:** JPEG or PNG images only. Video, audio, PDFs, documents, arbitrary URLs and client-supplied file metadata are not accepted.

For every evidence file, the server must resolve the delivery-specific evidence folder from trusted company/delivery configuration and verify:
- the exact Drive file ID exists and is not trashed;
- it has exactly one parent, the server-resolved folder for this company and delivery;
- trusted Drive metadata/app properties bind it to the same `company_id` and `delivery_id`;
- MIME type is allowlisted;
- access is restricted to authorized company administrators, dispatchers and the assigned driver; public access and link-sharing are disabled;
- the evidence row records the challenge, delivery, company, uploader, type and verified file metadata.

A client-provided Drive ID is only a lookup key, never proof that the file is authentic. The Drive adapter must verify ACLs and trusted metadata; folder naming or app properties alone are not an ACL. The production Drive adapter and upload flow are not currently wired. If an upload fails or a file cannot be retrieved/validated, registration fails and no evidence record can satisfy completion.

## Retry, recovery and exceptional cases

- **Wrong OTP:** increments attempts; no completion.
- **Expired/exhausted OTP:** invalidates the challenge; issue a new challenge only through the authorized flow.
- **Missing photo/evidence:** reject completion; delivery remains pending verification.
- **Recipient unreachable / recipient does not provide OTP / OTP lost:** do not mark delivered. The driver records a failed delivery attempt with a reason and escalates to dispatch under the existing failure/reoffer process. A dispatcher may reschedule or arrange another attempt. No supervisor/client flag, manual status edit or evidence-only bypass is provided.
- **Drive upload failure:** retry the upload through the authorized upload flow; do not invent a file reference or mark evidence verified.
- **Interrupted completion:** the challenge records `COMPLETING` with the exact request key, proof ID and evidence IDs. Retrying the same request can reconstruct a missing proof row and resume the idempotent state transition. A different key or evidence set is rejected.
- **Duplicate completion:** same key and same evidence returns the existing result; new key/replay is rejected. The state machine prevents a second completion event.

An exceptional completion override is deliberately not implemented. If the business later needs a no-OTP exception, it requires a separately reviewed policy with independent authorization, reason, alternative evidence, audit event and explicit customer-risk acceptance; it must not silently set `DELIVERED_VERIFIED`.

## Integration contract still required

Before enabling any operational endpoint, implement and verify:
1. A real server-side HMAC adapter backed by a secret unavailable to clients, and a cryptographically secure OTP generator.
2. An authenticated OTP delivery adapter with recipient-consent and send-failure behavior; no credentials in code or Git.
3. A Drive adapter that creates/uses the correct delivery folder, writes trusted `company_id`/`delivery_id` metadata, returns authoritative metadata, and verifies actual sharing permissions (including no public/link sharing).
4. A controlled upload path that accepts only allowed image types/size, uses server-side destination selection, and returns an opaque evidence ID—not an arbitrary Drive URL.
5. A live non-production Google test with synthetic recipients/files, multiple company accounts, assigned/unassigned drivers, real Sheets lock contention, Drive ACL checks and interruption/recovery.
6. An end-to-end review of the real entrypoint identity. Until the trusted Google identity entrypoint finding P0-01 is closed, `doPost` remains disabled and no operational endpoint is authorized.

## Evidence boundary

All tests in this branch use synthetic recipients, fake OTP delivery, fake Drive metadata/ACLs and fake store adapters. No real recipient, phone number, Drive file, Google Workspace resource or production data was used. **Drive permissions and end-to-end Google runtime have not been tested live.** Passing Node tests can verify service decision logic against its injected adapters; they cannot prove that a production adapter is correctly implemented or that Google ACLs are configured correctly.
